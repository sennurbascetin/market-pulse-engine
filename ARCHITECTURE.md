# Architecture

A deep dive on the data model, the transform logic and the analyst prompt design.
For setup and usage see [README.md](README.md).

---

## 1. Why an extended medallion

The classic Bronze/Silver/Gold split separates *raw*, *clean* and *analytics-ready*. This project
adds a fourth layer because the last stage does something categorically different from the first
three:

| Layer | Contains | Rebuildable from | Determinism |
|---|---|---|---|
| **Bronze** | exact source payloads | nothing — it *is* the record | n/a, append-only |
| **Silver** | typed, cleaned, deduplicated | Bronze | fully deterministic |
| **Gold** | metrics and aggregates | Silver | fully deterministic |
| **Platinum** | anomalies, sentiment, narratives | Gold + a model | **not** deterministic |

Platinum is where non-reproducible output lives. A narrative written by a language model cannot
be regenerated byte-for-byte, so it is stored with its full input context and provenance
(`provider`, `model`, `tokens_used`) rather than treated as a derived view. Keeping that
separate from Gold means the deterministic layers can always be dropped and rebuilt without
losing anything that cannot be recomputed.

### Idempotency as a design property

Every Bronze table has a deterministic natural key:

```python
quote_id   = sha256(ticker | observed_at | "snapshot")[:32]
article_id = sha256(url)[:32]
reading_id = sha256("cnn_fear_greed" | observed_at)[:32]
```

Combined with `ON CONFLICT DO NOTHING`, re-ingesting an unchanged observation is a no-op. This
is what makes the pipeline safe to run every 60 seconds against sources that only update every
few minutes: on a typical cycle 87 of 106 fetched articles are already known and are silently
discarded. The same property extends to `platinum.anomalies`, so the scan can re-cover any
window without producing duplicate alerts.

## 2. The transform layer

### Why DuckDB SQL rather than Pandas

The Gold transform is a single chained query — six CTEs over window functions:

```
base        session-stamped observations
reconciled  bar volume and cumulative volume unified into volume_delta
returns     previous price + session open
derived     intraday return, period return, log return
rolled      moving averages, volatility, VWAP, session position
scored      rolling mean/stddev feeding the z-scores
```

A full rebuild of 4,573 observations across 7 instruments takes **126 ms**. The equivalent
Pandas implementation would materialise several intermediate frames and loop per ticker.
Window sizes are injected from `config.py`, because a DuckDB frame bound cannot be a bound
parameter — `loader.py` substitutes only the known placeholder keys rather than using
`str.format`, so braces elsewhere in the SQL pass through untouched.

### The volume reconciliation problem

This is the subtlest part of the pipeline. Two sources describe volume differently:

| Source | `volume` means | `volume_basis` |
|---|---|---|
| `yfinance_history` (5-min bars) | traded **within** the bar | `bar` |
| `yfinance` (live snapshot) | session-to-date **cumulative** | `cumulative` |

Feeding both into the same rolling mean would compare a five-minute quantity against a
running total and flag nonsense. Gold reconciles them:

```sql
CASE
    WHEN volume_basis = 'bar' THEN volume
    ELSE GREATEST(
        volume - COALESCE(
            last_value(CASE WHEN volume_basis = 'cumulative' THEN volume END IGNORE NULLS)
                OVER (PARTITION BY ticker, session_date ORDER BY observed_at
                      ROWS BETWEEN UNBOUNDED PRECEDING AND 1 PRECEDING),
            volume),
        0)
END AS volume_delta
```

The `IGNORE NULLS` window finds the previous *cumulative* reading specifically, skipping any
interleaved bar rows. Two edges are deliberate:

* **The session's first cumulative reading contributes zero.** Its volume accrued before the
  engine started watching. Counting it as one interval's trade would manufacture an enormous
  false volume surge every time the pipeline starts mid-session — and the anomaly engine would
  dutifully report it.
* **`GREATEST(…, 0)` clamps a counter reset**, so a new session can never yield a negative delta.

### Session semantics

`session_date` is computed as `observed_at AT TIME ZONE 'America/New_York'` cast to a date, so a
13:30 UTC print and a 20:00 UTC print on the same US trading day group together. `intraday_return_pct`
is measured from the session's **first open**, not each observation's own open — otherwise a
5-minute historical bar would report a five-minute return under the name "intraday".

## 3. The anomaly engine

### The consensus rule

```python
anomaly = (|z| > 2.5) AND (value < Q1 - 1.5·IQR OR value > Q3 + 1.5·IQR)
```

Both arms are computed over the same trailing 60-observation window, in SQL — the quartiles via
`quantile_cont(…) OVER (…)` as a window function, so there is no NumPy round-trip. The decision
itself is pure Python (`is_consensus_anomaly`) and therefore directly unit-testable without a
database.

The two methods fail in different directions, which is the entire point:

* the **z-score** assumes approximate normality and is inflated by the outlier it is measuring,
  so a single extreme point raises its own window's standard deviation and partly masks itself;
* the **IQR fence** is distribution-free and unaffected by the outlier's magnitude, but it is
  coarse and ignores how far outside the fence a value sits.

**Measured effect on this dataset:** 13,707 metric evaluations produced 605 z-score-only flags;
requiring consensus cut that to 548 — a **9.4% reduction** in flagged events. Useful, and
smaller than the "dramatic" reduction often claimed for the technique. The honest summary is
that consensus trims the tail of marginal z-score hits rather than transforming the result.

### A deliberate blind spot

A perfectly flat trailing window has `Q3 - Q1 = 0`, giving a zero-width fence that would flag
*every* value differing at all. Such windows are rejected outright, which means **against a
perfectly constant baseline the engine confirms nothing, regardless of excursion size**. Real
instruments always carry tick-to-tick variation; a series flat to the cent is a data-feed
artefact, and staying silent on it is correct.

### Three metric families

| Type | Metric | Reads as |
|---|---|---|
| `volume_surge` | `volume_delta` | unusual participation |
| `price_spike` | `price` | dislocation from the recent mean |
| `volatility_burst` | rolling stddev of log returns | regime change |

Severity comes from `|z|`: ≥ 4.0 high, ≥ 3.0 medium, otherwise low.

## 4. Prompt design

### News sentiment

The system prompt fixes four things that a naive prompt gets wrong:

* **judge price impact, not tone** — "layoffs" is often bullish for a stock;
* **`neutral` is a real answer**, which stops the model manufacturing signal from routine
  coverage;
* **confidence is signal clarity, not outcome certainty**;
* **`tickers_impacted` may only contain watchlist symbols.**

That last constraint is *enforced*, not trusted: `validate_sentiment` intersects the returned
symbols with the configured watchlist, so a hallucinated ticker cannot reach Platinum. The
validator also normalises casing, clamps confidence to `[0, 1]`, and caps themes at three. Any
response that cannot be repaired raises `LLMError` and that single article degrades to the
offline analyst.

### The Market Pulse narrative

The analyst is handed a JSON block containing only measured facts — current prices and intraday
returns, this cycle's anomalies with their sigma values, the top scored headlines, and the
Fear & Greed reading — and is instructed to **use only those facts**, to explain *why* rather
than restate *what*, and to quote sigmas and percentages exactly as given. Grounding the model
in a fixed fact block is what keeps a "market commentary" feature from inventing causes.

The block is persisted verbatim in `platinum.market_pulse_narratives.context`, so any briefing
can be audited against exactly what its author saw.

### The offline analyst

Two bugs found while building it are worth recording, because both are the same mistake:

* `"ai"` matched inside `"em**ai**l"`, filing a phishing-scam article under *artificial
  intelligence*;
* `"no"` matched inside `"McKin**no**n"`, inverting a bullish headline to bearish.

Both were substring tests where word-boundary tests were needed. Lexicon matching without
`\b` anchors is quietly wrong on real text, and the failures are invisible until you read the
output.

## 5. Concurrency and failure

### One process, one database file

DuckDB permits one read-write process per file. `run.py` therefore runs APScheduler on a
background thread inside the Dash process. Each thread takes its own cursor via
`conn.cursor()` — DuckDB's supported multi-threading model — and writers serialise on a
process-wide `RLock`. The session is pinned to UTC so timestamps do not depend on the host's
locale.

### Degradation policy

| Failure | Behaviour |
|---|---|
| one RSS feed down | recorded in `IngestResult.errors`, others proceed |
| Fear & Greed endpoint changes shape | soft failure, dashboard shows "unavailable" |
| LLM request fails or returns junk | that item falls back to the offline analyst |
| a whole stage raises | run marked `partial`, scheduler continues |
| ≥ 3 stage failures | run marked `failed`, scheduler still continues |
| index damaged by an unclean shutdown | table rebuilt in place, transform retried once |
| a second instance is started | the holding PID is reported, exit code 2 |

### The index-damage failure, in full

DuckDB maintains an ART index behind every `PRIMARY KEY`. A process killed mid-write can leave
it inconsistent with the table's rows; the next statement that must *delete* an index entry then
aborts the entire database instance:

```
FATAL Error: Invalid Input Error: Failed to delete all rows from index.
Only deleted 0 out of N rows.
```

This was reproduced deterministically on an affected file, while a fresh database ran the same
statements indefinitely — so it is recoverable damage, not a DuckDB limitation. Both
`INSERT OR REPLACE` and `ON CONFLICT DO UPDATE` take the failing delete path;
`ON CONFLICT DO NOTHING` does not.

The response is layered:

1. **Prevention.** `run.py` installs SIGINT/SIGTERM/SIGHUP handlers and an `atexit` hook, so
   Ctrl-C, `kill` and `docker stop` all checkpoint the file. Without this the Dash server blocks
   in `serve_forever` and SIGTERM kills the process with no cleanup at all.
2. **Avoidance.** The immutable Silver tables use `ON CONFLICT DO NOTHING` — more accurate
   semantics for an article or a published reading, and it never touches the delete path.
3. **Recovery.** `db/repair.py` detects the abort, copies the table aside, drops and recreates it
   from `schema.sql` (rebuilding the index), restores every row, and retries once. Nothing is
   regenerated from upstream: Bronze payloads and LLM-authored Platinum records cannot be
   recomputed. A second failure is re-raised rather than hidden.

The scheduler is configured with `coalesce=True` and `max_instances=1`, so a slow cycle can
never stack up behind the next tick.

### Market-hours awareness

Outside the regular session the price leg is restricted to instruments that actually trade
round the clock; polling a closed exchange just re-reads the same close. News and the sentiment
index never stop. `mode` on each run log row records which regime applied.

## 6. Serving

All dashboard SQL lives in `dashboard/queries.py` rather than inside callbacks, so the serving
layer has one reviewable data contract and any panel's query can be pasted into a DuckDB shell.
Every query returns an empty structure on failure, so the board renders on the first page load —
before the first cycle has finished.

One callback repaints the eight panels that share a refresh; the price chart has its own so that
changing ticker repaints instantly rather than waiting for the interval.

Price and volume are drawn as **two stacked subplots sharing an x-axis**, never as a dual-axis
chart. Two y-scales on one plot let an arbitrary alignment imply a correlation the data does not
contain — it is the most common way a financial chart misleads.
